# Local service readiness and query-plan proof

## Scope

This proof uses only the loopback Supabase stack and synthetic `opord006-plan-*` identities inside one PostgreSQL transaction. It does not contact a hosted project, expose credentials, or reset the local stack. Fixture rows are rolled back, then the script runs `VACUUM (ANALYZE)` on the touched tables because PostgreSQL planner statistics are not transactional and aborted inserts leave dead tuples. Exact table counts are compared before and after, and the retained browser family is independently reverified.

## Service recovery contract

The app has one client service contract with durable-local, memory-test, and configured-Supabase adapters. Configured failures never fall back to family fixtures. The Supabase adapter wraps every synchronous throw and rejected promise with the central non-sensitive categories in `serviceErrors.ts`; feature mutations keep user input and expose an explicit retry.

TanStack Query makes the retry boundary explicit:

- reads retry at most once;
- writes never retry automatically, so the client does not replay them on its own;
- user-driven retries refetch server-authoritative state, but a message/event insert whose response was lost has no idempotency key and may duplicate when manually retried;
- media uses its persisted pending/active/deleting protocol instead of replaying an opaque upload;
- there is no client-generated correlation ID, general request version header, universal request deadline, or client-side rate limiter.

The omitted controls require a cooperating server/gateway and operational logging. Inventing client-only correlation IDs or automatically timing out/replaying writes would not prove propagation and could make recovery less safe. Hosted readiness/liveness endpoints, correlation propagation, gateway rate enforcement, timeout policy, and telemetry therefore remain `NOT RUN` rather than being simulated in the UI.

## Representative database fixture

Run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-local-supabase-query-plans.ps1
```

The transaction adds 20 members to one synthetic family, 100 ordered events, 20 exact-event RSVPs, 100 ordered comments on one event, 50 active media rows on that event, 20 exact-user/event reminder rows, and the normal per-recipient notifications generated by event, RSVP, and comment triggers. It captures `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` for the actual adapter filters and orderings, asserts exact bounded result counts and a 100 ms local ceiling, rolls the rows back, removes dead fixture tuples, and refreshes statistics from the retained rows.

The retained baseline before and after the accepted run was exactly `8,2,6,5,9,9,4,60,1` for profiles, groups, memberships, events, RSVPs, messages, media, notifications, and reminders. The independent populated-scenario verifier remained 4 identities, 3 members, 3 trips, 6 messages, 6 RSVPs, 3 media, 38 notifications, 0 reminders, 3 Storage objects, and zero outsider residue.

## Query and index disposition

| Adapter path | Representative result | Accepted plan | Disposition |
|---|---:|---|---|
| Group events by `group_id`, `starts_at ASC` | 100 | sequential scan + in-memory sort, 0.037 ms | Legitimate: all 100 synthetic events match and the table is tiny. |
| Exact event by primary ID | 1 of 105 | sequential scan, 0.014 ms | Legitimate: the whole table occupies too little space for an index to win. |
| Messages by `event_id`, `created_at ASC`, `id ASC` | 100 | sequential scan + sort, 0.048 ms | Legitimate: all 100 synthetic comments match the selected event. |
| Active media by `event_id`, `uploaded_at DESC` | 50 | sequential scan + sort, 0.047 ms | Legitimate: all 50 synthetic media rows match; the existing event index remains available at larger/selective distributions. |
| RSVPs by `event_id` | 20 | sequential scan, 0.012 ms | Legitimate: all representative RSVPs match and the composite primary key enforces uniqueness. |
| Exact reminder by event/user/enabled | 1 | sequential scan, 0.011 ms | Legitimate at 21 total rows; the `(event_id,user_id)` primary key enforces identity. |
| Group/event membership helpers | 1 | result in 0.103/0.199 ms | Security-definer helpers returned the exact allowed path; existing composite keys enforce membership identity. |
| All notifications by `user_id`, newest first | 214 of 3,860 | sequential scan + sort, under 1 ms | This is the live notification-screen query and remains bounded at representative volume. |

An exploratory candidate on `(user_id, created_at DESC)` improved the adapter's limit-12 `listRecentActivity()` method, but repository tracing found no production caller for that method. The live notification screen requests the full user history, and the candidate did not improve that measured query. The candidate was therefore rejected and removed; no migration or speculative index remains. The checked-in harness measures only production-relevant queries and existing membership helpers.

## Recovery and operational limits

- Migration checksums protect all historical files. Do not edit an applied migration.
- If a hosted plan regresses, capture the hosted plan and table statistics before proposing another index; representative local data is not production cardinality evidence.
- Hosted migration state, connection-pool saturation, slow-query telemetry, rate limits, correlation IDs, and production alerting remain `NOT RUN` without a named authorized target.
